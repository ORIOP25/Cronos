# Testing and CI

Cronos has one test suite with one result.
The browser E2E journeys prove that the application works end to end through the visible UI.
The backend and frontend gates cover only the essential core, so they stay fast.
After a green run on `main`, one read-only job confirms that production serves that commit.
There is no separate production test campaign.

Cronos runs backend, frontend, and end-to-end suites through one root runner.
GitHub Actions enforces the same gates on every pull request and on every push to `main`.
A feature branch with an open pull request runs the full pipeline once through the pull request, instead of a second identical push run.
A branch pushed without a pull request has no automatic CI and requires an explicit manual `workflow_dispatch` checkpoint.

## Quick start

The supported entry point is the root runner:

```powershell
node scripts/test.mjs setup --scope all
node scripts/test.mjs doctor --profile all
node scripts/test.mjs fast --scope all
node scripts/test.mjs critical --scope backend
node scripts/test.mjs integration
node scripts/test.mjs e2e --project public
node scripts/test.mjs capacity-smoke
node scripts/test.mjs all --scope all
node scripts/test.mjs benchmark --profile fast
node scripts/test.mjs campaign --manifest backend/tests/scheduler_lab/manifest.json
```

The runner exposes `setup`, `doctor`, `fast`, `critical`, `integration`, `e2e`, `capacity`, `capacity-smoke`, `all`, `benchmark`, and `campaign`. The `e2e` command accepts `--project public|auth|app|isolated|readonly|provider|capacity`. The `critical` command accepts only `--scope backend` and is the fast required CI gate. E2E starts its own stack on port `5174`.

`fast` never starts Docker or installs packages. Forwarded arguments are accepted only after `--` by `fast` and `integration`, and are passed as separate process arguments. Run artefacts are written to `.test-artifacts/`.

## Backend suites

The fast required gate runs the critical selection, not the full corpus.

`node scripts/test.mjs critical --scope backend` reads `backend/tests/critical_manifest.json`, generated by `backend/tests/critical_selection.py` and guarded by `backend/tests/unit/test_critical_selection_policy.py`.

The manifest declares two groups. The `unit` group runs the 23 critical unit files with two workers and the loopback-only socket policy. The `db` group runs 9 database files plus 2 exact webhook node IDs with four workers, against the real PostgreSQL/Redis stack and the Alembic schema.

The critical coverage gate requires 80 percent over 18 declared sources; `constraint_policy.py` stays at 100 and `candidate_validation.py` at 90. The runner parser requires a non-empty, unique, in-scope selection and the exact 100 and 90 protected policies. Each group writes its own coverage file; the runner combines them and fails on any empty group, missing JUnit or skipped test.

The full corpus is deselected, never deleted. The optional full run keeps the whole-application coverage default of 70 percent and the structural suite table.

| Suite | Location | Execution |
| :--- | :--- | :--- |
| Unit | `backend/tests/unit/` | no database or external network; loopback-only socket policy |
| Transactional integration | `backend/tests/integration/transactional/` | real PostgreSQL/Redis stack |
| Committed integration | `backend/tests/integration/committed/` | real PostgreSQL/Redis stack, xdist=4 |
| Contracts | `backend/tests/contracts/` | real PostgreSQL/Redis stack, serial |

Suite membership is structural. PostgreSQL migrations always run through Alembic; SQLite and `metadata.create_all` are not valid substitutes. The runner creates `cronos_test_gw0` through `cronos_test_gw3` for xdist and uses separate migrator/runtime credentials. Destructive operations are accepted only for exact test database names.

The optional full run uses `-n 4 --dist=loadscope` and keeps the rate-limited contracts. `pyproject.toml` keeps the whole-application coverage default and no include list, so the manual full report stays honest.

## Frontend suites

The 48-class correctness test uses the production 900-second safety budget and stops at the first complete candidate.
It validates curricular coverage and completion dates. Short optimization deadlines must not make correctness depend on host load.

The fast required frontend gate is `npm run verify:critical:fast`, a self-contained macro.
It runs the legal and marketing-build contracts, the edge worker, the marketing assets and the critical coverage.
It does not run the full-source lint, the production dependency audit, the repository script tests, Knip or the production build.
Those five checks are mandatory and unconditional in the long `e2e-runtime` job, after the frontend dependency install.
The optional developer `npm run verify:critical` keeps `verify:checks`, the critical coverage and the build; the full `npm run verify` stays at 587 cases.
Critical mode (`vitest run --mode critical`) selects 24 files and 254 cases from `frontend/src/test/criticalSelection.js`: the node, dom and dom-network projects, the network guard and the selection guard.
It keeps `envDir: false`, `isolate: true`, the fail-closed network guard and 31 declared modules at 45/40/35/45.

Vitest is configured in `frontend/vitest.config.js` with isolated `node`, `dom` and `dom-network` projects and thread pooling. Only the `dom-network` project keeps the MSW server with strict unhandled-request failures. Every other DOM test replaces `fetch` and `XMLHttpRequest` with a fail-closed guard that throws a classified `TestNetworkDeniedError`, so no accidental external request leaves the process. Coverage uses V8 and enforces thresholds of 45 percent statements, 40 percent branches, 35 percent functions, and 45 percent lines. React interactions that cross async boundaries use Testing Library `user-event`.

Playwright is configured in `frontend/playwright.config.js`. The `setup` project feeds `auth` and `auth-state`; the `public` project needs no authentication and no `setup` dependency. The shared chain is `auth-state` → `app` → `provider` → `readonly`. The `isolated` project depends on `setup` and covers fresh-or-existing journeys that create and clean their own user or organization. The `readonly` project depends on `provider` and runs after it, so the tutorial and localStorage-only journeys never race the shared soft-reset. The `app`, `provider`, `isolated` and `readonly` projects use one worker; independent projects receive a global fan-out of two workers, `auth` is bounded to two and `capacity` uses two. The retired `faults` project now maps to the two `isolated` and `readonly` case paths. The `capacity` project runs only when `CAPACITY_ENABLED=1`. Retries are disabled; traces are retained on failure and screenshots are captured on failure.

All projects use the shared `E2E_BASE_URL`, which defaults to `http://127.0.0.1:5174`.
This address matches the owned Docker stack's IPv4 binding and avoids other processes listening on `localhost` over IPv6.
The runner supplies `http://localhost:5173` for an external stack.

After sign-in, the E2E helper waits for the loaded Clerk session and expected identity before activating the organization.
This prevents organization activation during a sign-in navigation while the browser reloads Clerk.

## CI gates

The owned local E2E stack builds the frontend `ci` target, which permits the dedicated Clerk test domain.
Its Nginx application routes include `/imports`. Production keeps its runtime browser policy.

GitHub Actions keeps backend, frontend and E2E in separate jobs. The backend job has a 45-minute timeout, the frontend job has a 20-minute timeout, and the E2E job has a 30-minute timeout.

Backend gates use Python 3.14 with `postgres:16` and `redis:7` services. The job provisions `cronos_migrator`, `cronos_app`, and `cronos_auth_definer` and installs locked dependencies with `--require-hashes`. One merged stage then runs `pip check` and `pip-audit` in the background, Ruff in the foreground, Alembic upgrade/check/downgrade/upgrade, and the trigger and integrity audits with the migrator credential; both the background audit and the foreground gates must pass. The job then runs the critical core with `node scripts/test.mjs critical --scope backend`. The runner is a Node CLI, so the job sets up Node without installing packages. The job builds the hardened runtime image.

Frontend gates use Node 24 with `npm ci --ignore-scripts` and then the self-contained `npm run verify:critical:fast`, which runs the legal, marketing-build, edge, asset and critical-coverage steps. The full-source lint, the production dependency audit and the repository script tests run in the long `e2e-runtime` job instead. The job also runs `node scripts/loc-report.mjs` against `documentation/08_security_quality/loc-baseline.json`.

E2E is two jobs plus one aggregate. `e2e-runtime` needs no Clerk or provider credential, so it is mandatory on every pull request, including Dependabot and forks; it runs 9 real worker-recovery cases plus the single full 48-class typology proof, 10 collected with zero skips, against native PostgreSQL/Redis, and it also runs the whole-source frontend lint, the production dependency audit, the repository script tests, the whole-system frontend Knip and the production build. `e2e-browser` runs the browser UI journeys against the full CI stack and the 2 capacity cases; the Dependabot or fork policy skips only this job, which needs the Clerk SDK. The aggregate `e2e` job fails unless `e2e-runtime` succeeded and `e2e-browser` succeeded or was skipped by that policy. The guarded upload keeps the runner `run.json` metadata always and the Playwright `e2e-all.xml` only when the E2E step passed; it never adds auth state, binaries, logs or private files.

## Production deployment check

The `production` job runs only for a push to `main`, after `backend`, `frontend` and `e2e` pass.
It runs `scripts/verify-production-deploy.mjs` with the pushed commit as `EXPECTED_REVISION`.
The script waits up to 20 minutes, because the deployments start on the same push as CI.

The check is read-only. It uses no credentials, creates no accounts and makes no business writes.
It passes when all of these are true:

- `https://cronos.pt/revision.json` reports the expected commit.
- `https://api.cronos.pt/health/ready` reports `ok`, with PostgreSQL and Redis connected.
- The API reports the expected commit, when the commit changed `backend/`.
- `/` and `/login` answer with the application shell.

Railway redeploys the API only for backend changes, so a frontend-only commit keeps the previous API revision.
A failure prints each unmet condition as a workflow error.
