# Testing and CI

Cronos has one test suite with one result.
The browser E2E journeys prove that the application works end to end through the visible UI.
The backend and frontend gates cover only the essential core, so they stay fast.
After every push to `main`, the separate Deploy check workflow confirms that production serves that commit.
There is no separate production test campaign.

Cronos runs backend, frontend, and end-to-end suites through one root runner.
GitHub Actions enforces the same gates on every pull request and on every push to `main`.
A push to `main` skips the suites when its merged pull request head has the same tree and already passed `backend`, `frontend`, `e2e-runtime` and `e2e-browser`.
Any other push to `main` runs every gate again.
A feature branch with an open pull request runs the full pipeline once through the pull request, instead of a second identical push run.
A branch pushed without a pull request has no automatic CI and requires an explicit manual `workflow_dispatch` checkpoint.

## Quick start

The supported entry point is the root runner:

```powershell
node scripts/test.mjs setup --scope all
node scripts/test.mjs doctor --profile all
node scripts/test.mjs fast --scope all
node scripts/test.mjs critical --scope backend
node scripts/test.mjs integration
node scripts/test.mjs e2e --project public
node scripts/test.mjs capacity-smoke
node scripts/test.mjs all --scope all
node scripts/test.mjs benchmark --profile fast
node scripts/test.mjs campaign --manifest backend/tests/scheduler_lab/manifest.json
```

The runner exposes `setup`, `doctor`, `fast`, `critical`, `integration`, `e2e`, `capacity`, `capacity-smoke`, `all`, `benchmark`, and `campaign`. The `e2e` command accepts `--project public|auth|app|isolated|readonly|provider|capacity`. The `critical` command accepts only `--scope backend` and is the backend CI gate. E2E starts its own stack on port `5174`.

`fast` never starts Docker or installs packages. Forwarded arguments are accepted only after `--` by `fast` and `integration`, and are passed as separate process arguments. Run artefacts are written to `.test-artifacts/`.

## Backend suites

The fast required gate runs the critical selection, not the full corpus.

`node scripts/test.mjs critical --scope backend` reads `backend/tests/critical_manifest.json`, generated by `backend/tests/critical_selection.py` and guarded by `backend/tests/unit/test_critical_selection_policy.py`.

The manifest declares two groups. The `unit` group runs the 21 critical unit files with two workers and the loopback-only socket policy. The `db` group runs 9 database files plus 2 exact webhook node IDs with four workers, against the real PostgreSQL/Redis stack and the Alembic schema (CI provides the services).

The critical coverage gate requires 80 percent over 18 declared sources; `constraint_policy.py` stays at 100 and `candidate_validation.py` at 90. The runner parser requires a non-empty, unique, in-scope selection and the exact 100 and 90 protected policies. Each group writes its own coverage file; the runner combines them and fails on any empty group, missing JUnit or skipped test.

The full corpus is deselected, never deleted. The optional full run keeps the whole-application coverage default of 70 percent and the structural suite table.

| Suite | Location | Execution |
| :--- | :--- | :--- |
| Unit | `backend/tests/unit/` | no database or external network; loopback-only socket policy |
| Transactional integration | `backend/tests/integration/transactional/` | real PostgreSQL/Redis stack |
| Committed integration | `backend/tests/integration/committed/` | real PostgreSQL/Redis stack, xdist=4 |
| Contracts | `backend/tests/contracts/` | real PostgreSQL/Redis stack, serial |

Suite membership is structural. PostgreSQL migrations always run through Alembic; SQLite and `metadata.create_all` are not valid substitutes. The runner creates `cronos_test_gw0` through `cronos_test_gw3` for xdist and uses separate migrator/runtime credentials. Destructive operations are accepted only for exact test database names.

The optional full run uses `-n 4 --dist=loadscope` and keeps the rate-limited contracts. `pyproject.toml` keeps the whole-application coverage default and no include list, so the manual full report stays honest.

## Frontend suites

The 48-class correctness test uses the production 900-second safety budget and stops at the first complete candidate.
It validates curricular coverage and completion dates. Short optimization deadlines must not make correctness depend on host load.

The fast required frontend gate is `npm run verify:critical:fast` (see CI gates). `npm run verify:checks` adds lint, both Knip runs and the script tests; `npm run verify` adds the full coverage run and the build.
Critical mode (`vitest run --mode critical`) selects the files listed in `frontend/src/test/criticalSelection.js`: the `node`, `dom` and `dom-network` projects, the network guard and the selection guard. It keeps the fail-closed network guard and the 45/40/35/45 coverage floors over the declared critical sources.

Vitest is configured in `frontend/vitest.config.js` with isolated `node`, `dom` and `dom-network` projects and thread pooling. Only the `dom-network` project keeps the MSW server with strict unhandled-request failures. Every other DOM test replaces `fetch` and `XMLHttpRequest` with a fail-closed guard that throws a classified `TestNetworkDeniedError`, so no accidental external request leaves the process. Coverage uses V8 and enforces thresholds of 45 percent statements, 40 percent branches, 35 percent functions, and 45 percent lines. React interactions that cross async boundaries use Testing Library `user-event`.

Playwright is configured in `frontend/playwright.config.js`. The `setup` project feeds `auth` and `auth-state`; the `public` project needs no authentication and no `setup` dependency. The shared chain is `auth-state` → `app` → `provider` → `readonly`. The `isolated` project depends on `setup` and covers fresh-or-existing journeys that create and clean their own user or organization. The `readonly` project depends on `provider` and runs after it, so the tutorial and localStorage-only journeys never race the shared soft-reset. The `app`, `provider`, `isolated` and `readonly` projects use one worker; independent projects receive a global fan-out of two workers, `auth` is bounded to two and `capacity` uses one. The `capacity` project runs only when `CAPACITY_ENABLED=1`. Retries are disabled; traces are retained on failure and screenshots are captured on failure.

All projects use the shared `E2E_BASE_URL`, which defaults to `http://127.0.0.1:5174`.
This address matches the owned Docker stack's IPv4 binding and avoids other processes listening on `localhost` over IPv6.
The runner supplies `http://localhost:5173` for an external stack.

After sign-in, the E2E helper waits for the loaded Clerk session and expected identity before activating the organization.
This prevents organization activation during a sign-in navigation while the browser reloads Clerk.

## CI gates

`.github/workflows/ci.yml` runs on every pull request, every push to `main` and on manual `workflow_dispatch`. Concurrent runs of the same ref cancel the older one. Permissions are `contents: read`. Python is 3.14 and Node is 24.

| Job | Timeout | What it enforces |
| :--- | ---: | :--- |
| `already-verified` | default | On a push to `main` only. Looks up the merged pull request of the pushed commit and reports `verified=true` when that head has the same Git tree and the `backend`, `frontend`, `e2e-runtime` and `e2e-browser` checks all succeeded. |
| `backend` | 45 min | `postgres:16-alpine` and `redis:7-alpine` services (pinned by digest). Provisions roles with `sh backend/scripts/provision_database.sh`, then the `cronos_test_gw0`..`cronos_test_gw3` databases. Installs `requirements-dev.txt` with `--require-hashes`. One stage runs `pip check` and `pip-audit` in the background, `ruff format --check`, `ruff check`, Alembic `upgrade head`, `check`, `downgrade base`, `upgrade head`, then `scripts.audit_triggers` and `scripts.audit_database_integrity` with the migrator credential. Then `node ../scripts/test.mjs critical --scope backend`. For pull requests from forks only it also builds the `runtime` image and checks the `privacy.run_maintenance` task. |
| `frontend` | 20 min | `npm ci --ignore-scripts`, `npm run verify:critical:fast`, then `node scripts/loc-report.mjs`. |
| `e2e-browser` | 30 min | Skipped for Dependabot and fork pull requests (it needs Clerk). Builds `docker-compose.ci.yml`, verifies the production image and the privacy task, starts `db` and `redis`, provisions roles with the `provision-db` service, migrates with `db-maintenance`, starts `backend worker beat frontend`, prepares the Clerk test state, then runs `node scripts/test.mjs e2e` and `capacity-smoke`. |
| `e2e-runtime` | 25 min | Needs no Clerk or provider credential, so it runs on every pull request. Native PostgreSQL/Redis. Runs `npm run lint`, `audit:production`, `test:scripts`, `lint:dead-code`, `lint:dead-code:production` and `build`; then `test_worker_process_recovery.py` plus `test_forty_eight_classes_generate_a_complete_valid_schedule`. A script fails the job if fewer than 10 cases were collected, if any case was skipped or failed, or if the three required case names are missing. |

There is no aggregate job; the four suite checks are `backend`, `frontend`, `e2e-runtime` and `e2e-browser`.

`frontend` is the fast gate: `verify:critical:fast` runs the legal-version contract, the marketing-build tests, the edge worker test, the marketing asset audit and the critical Vitest coverage. Lint, the production dependency audit, the repository script tests, Knip and the production build are deliberately in `e2e-runtime`.

### Secrets and variables

The workflows use exactly one secret and one variable:

| Name | Kind | Used by |
| :--- | :--- | :--- |
| `CLERK_SECRET_KEY` | secret | `e2e-browser` (must start with `sk_test_`). |
| `VITE_CLERK_PUBLISHABLE_KEY` | variable | `e2e-browser` (must start with `pk_test_`). |

Database passwords are generated per run (`openssl rand -hex 24`), masked and never stored. No `CLERK_WEBHOOK_SECRET`, Cloudflare, Sonar or Postgres password secret exists. E2E identities are dedicated Clerk reserved test users (`+clerk_test@example.com`); the job revokes its invitations at the end.

### Critical and full selections

| Selection | Backend | Frontend | Coverage |
| :--- | :--- | :--- | :--- |
| Critical (required in CI) | 21 unit files, 9 database files and 2 webhook node IDs from `critical_manifest.json` | 24 files from `criticalSelection.js` (`vitest run --mode critical`) | 18 declared backend sources at 80 percent, `constraint_policy.py` at 100 and `candidate_validation.py` at 90; frontend critical sources at 45/40/35/45 |
| Full (manual) | whole unit, integration and contract corpus | `vitest run` | whole application: 70 percent backend, 45/40/35/45 frontend |

The full corpus is deselected from the required gates, never deleted. Use `node scripts/test.mjs all --scope all` or `npm run verify` for it. Skipped tests, retries, missing artifacts and migration drift are release failures.

## Production deployment check

`.github/workflows/deploy-check.yml` runs the `production` job on every push to `main`, independently of CI, because Railway and Cloudflare Pages deploy every push.
It runs `scripts/verify-production-deploy.mjs` with the pushed commit as `EXPECTED_REVISION`, then `frontend/scripts/verify-production-browser.mjs` in Chromium.
The first script waits up to 20 minutes, because the deployments start on the same push as CI.

The check is read-only. It uses no credentials, creates no accounts and makes no business writes.
It passes when all of these are true:

- `https://cronos.pt/revision.json` reports the expected commit.
- `https://api.cronos.pt/health/ready` reports `ok`, with PostgreSQL and Redis connected.
- The API reports the expected commit, when the commit changed `backend/`.
- `/` and `/login` answer with the application shell.
- In Chromium, `/` shows its heading and `/login` shows the Clerk email and password fields, with no JavaScript error and no failed `cronos.pt` resource.

Railway redeploys the API only for backend changes, so a frontend-only commit keeps the previous API revision.
A failure prints each unmet condition as a workflow error.
